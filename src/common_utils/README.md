# Common utilities

`src.common_utils` contains shared helpers used across multiple stages of the
public pipeline. For users, the most important responsibility here is the
template/production energetics synchronization workflow used by Stage 4.

Commonly relevant pieces:

- `common_init.py` — shared YAML/CLI initialization used by Stages 1 and 2
- `utils.py` — shared logging setup and small helpers
- `energetics_io.py` — energetics loading, comparison, and mismatch handling
- `synchronizer.py` — CLI helper for repairing out-of-sync energetics files

## Energetics synchronization

This module explains why the "energetics template" (generated by the
jump-network builder) and the production energetics YAML (used by numeric
evaluators) must remain synchronized, how the repository checks their
compatibility, and how to use the `synchronizer` helper to keep the production
file aligned with the template.

Why template and production must be in sync
------------------------------------------
- The symbolic and numeric diffusion coefficient calculations rely on a fixed mapping between "global jump indices"
  (integers used internally in symbolic expressions) and the physical jump descriptions in your YAML file
  (pair labels, geometry/length, site-to-site jump directions).
- If the jump-network builder regenerates the template (for example after changing cutoff settings that affect
  which neighbor pairs are considered), the template's ordering or the numbering of global jumps may change.
- If the production YAML (the file used to supply barrier heights and frequencies) is not updated to match the
  new template, the numeric evaluation will substitute wrong energies/frequencies for the symbolic weights and
  produce incorrect diffusion coefficients. This is a frequent, subtle source of error; therefore synchronization
  is mandatory whenever the template changes.

How the check works (compare_energetics)
----------------------------------------
The repository provides a programmatic comparator `compare_energetics(template_path, production_path, length_tolerance)`
located in `src.common_utils.energetics_io`. The comparator implements the following rules:

- It reads the `jumps` mapping from both YAML files. Each `jumps` entry is a mapping from a `pair_key` (e.g. `A-H`)
  to a list of jump entries.
- For matching the template to the production file it prefers a structural match by (pair_key, length) rather than
  by global indices. This is robust against global renumbering of the indices when the template is regenerated.
- Lengths are compared with a tolerance (float). The tolerance is taken from `settings.length_tolerance` if present
  in either YAML, or may be passed explicitly to the comparator. If lengths are missing for an entry the comparator
  falls back to matching by `pair_key` only.
- The comparator reports:
  - `template_n_jumps` and `production_n_jumps` (counts of jump entries)
  - `missing_template_entries` — template jumps that are not found in production
  - `extra_production_entries` — production jumps that are not present in template
  - `mismatches` and the length tolerance used

If the comparator reports any differences the evaluator should not proceed without inspection.

How the synchroniser works (synchronize_energetics)
-------------------------------------------------
Use the `synchronize_energetics(template_path, production_path, out_dir=None, length_tolerance=None)` helper
to produce a new production YAML that is aligned with the current template. Key behaviors:

- The synchroniser walks the template `jumps` structure in the order provided by the template and for each
  template entry attempts to find a matching production entry by `pair_key` and `length` (within tolerance).
- If a match is found, the synchroniser copies over energetic data from production (e.g. `energy_sp`, `frequency`).
- If a template entry is new (no match found), the synchroniser inserts a placeholder entry where the `energy_sp`
  field is set to a commented `None` value (the repository uses `CommentedData(None, commented=True)` so that
  ruamel.yaml writes it as a YAML comment). This makes new entries visible but prevents silent, incorrect numeric
  substitutions.
- Production-only jumps (entries that exist in production but not in template) are omitted from the new file and the
  user is warned.
- The new production file is written alongside the provided production file (or into `--out-dir`), and the
  filename is suffixed with `_<n_fq>freq.YAML` where `n_fq` is the number of unique global jump indices referenced by
  the synchronized `jumps` (each forward/backward index is counted independently). This naming convention makes it
  explicit how many frequencies the new YAML contains.

CLI: `synchronizer` script
-------------------------
There is a small CLI wrapper in `src/common_utils/synchronizer.py`. Usage examples:

1) Minimal (from the `public` folder):

   python -m src.common_utils.synchronizer /path/to/energetics_template.yaml /path/to/production_energetics.yaml

2) Specify output directory and length tolerance:

   python -m src.common_utils.synchronizer template.yaml production.yaml --out-dir production_dir --length-tolerance 0.05

3) Dry-run (do not write file):

   python -m src.common_utils.synchronizer template.yaml production.yaml --dry-run --verbose

The CLI prints a human-readable `report` with the numbers of copied entries, placeholder entries and the new
filename. With `-v/--verbose` it also prints the planned path and a small JSON blob for piping to other tools.

Manual steps required after synchronization
------------------------------------------
- Any placeholder entries (commented `energy_sp`) must be filled in by hand with the correct saddle-point energy
  (barrier) values. These placeholders are intentionally commented so the user notices them.
- Open the produced YAML, locate entries similar to:

  jumps:
    A-H:
      - jump_id:
          forward: 3
          backward: 5
        length: 2.465017
        energy_sp: # None

  Replace the commented placeholder with a numeric value, e.g.:

        energy_sp: 0.71

  Ensure the YAML indentation is preserved (two spaces per level as in the repository style) and that you do not
  accidentally uncomment or remove important comments or keys.

Principles and decisions made
----------------------------
- Matching by `pair_key` and `length` (with tolerance) was chosen over matching by global indices. This is
  deliberate: if cutoffs or neighbor selection change and the template is regenerated the global numbering will likely
  change — matching by pair/length is more stable and preserves the user's energetics when possible.
- When multiple production entries match a template entry (rare), the synchroniser picks the first unused match found.
  This heuristic keeps the logic simple but may require manual inspection in edge cases; the comparator report helps
  find ambiguous situations.
- The synchroniser never overwrites the original production file. It writes a new file using the `_<n_fq>freq.YAML`
  suffix so you can review the changes and adopt the new file when ready.

Recommended workflow
--------------------
1) Regenerate the template (run the jump-network builder) if you changed geometry/cutoffs.
2) Run the comparator and inspect results: either call `compare_energetics(...)` from Python or run the CLI in verbose
   dry-run mode.
3) If differences are detected, run the synchroniser (dry-run first, then actual run).
4) Edit the produced file and replace commented placeholders with correct `energy_sp` values. Double-check `frequency`
   entries as well — forward/backward frequencies may differ for non-symmetric jumps.
5) Re-run the comparator and the evaluator. Keep the new synchronized file under version control (recommended).

Suggested integration point
---------------------------
It is helpful for the `transport_coefficient_evaluator` to check template/production compatibility before numeric
evaluation. A small guard can be added at the beginning of `src/transport_coefficient_evaluator/evaluator.py` (or the
CLI wrapper that invokes it) to call `compare_energetics(...)` and print a short user-facing warning with a pointer to
this README, for example:

```python
from src.common_utils.energetics_io import compare_energetics

ok, details = compare_energetics(template_path, production_path)
if not ok:
    print("WARNING: energetics template and production are out of sync. See src/common_utils/README.md for details.")
    print(details)
    # Optionally: abort or prompt user to run synchronizer
```

FAQ / Troubleshooting
---------------------
- Q: The evaluator warns that the template and production energetics are out of sync. What does that mean?
  A: The jump list in `energetics_template.yaml` no longer matches the hand-edited
     production energetics file. Typical causes are changes to geometry,
     pair-specific cutoffs, or neighbour selection that regenerated the template
     with different jump lengths or numbering. Run the synchronizer or manually
     align the production file before trusting numeric diffusion coefficients.

- Q: The evaluator says `dc expression file not found`.
  A: Stage 4 expects a Stage-3 output file such as
     `dc_symbolic_<h>_<k>_<l>.txt`. Run the transport-coefficient solver first
     or point the evaluator at the correct file.

- Q: Automatic synchronization failed and the evaluator stopped.
  A: This means `DC_AUTO_SYNC=1` was set, the code attempted to repair the
     production energetics file automatically, and that synchronization itself
     failed. Run `python -m src.common_utils.synchronizer ...` manually and fix
     any placeholder `energy_sp` entries before retrying.

- Q: The synchroniser created many placeholder entries — what now?
  A: This means the production file lacks energetics for jumps present in the template. You must provide saddle-point
     energies for these jumps manually. If many placeholders appear, review whether you intended the template changes
     (e.g., did you change cutoffs?) and revert or adjust if necessary.

- Q: The comparator reports mismatches even though pair keys look the same.
  A: Check numeric lengths and the `settings.length_tolerance` value. If necessary increase the tolerance or confirm the
     template's lengths are correct.

- Q: Should I edit the template directly to add energetics?
  A: No — energetic parameters belong in production YAML files (these are the inputs for numeric evaluation). The
     template is a generated mapping of jump geometry and should remain a representation of the network only.
